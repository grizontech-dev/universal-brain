POST api.tavily.com/search api_key: {TAVILY_API_KEY} query: {query} max_results: 5
🔄 Automatic fallback: If Tavily fails or is unavailable, the call falls through to Brave. If Brave also fails, returns { results: [], engine: "none" }. The LLM handles empty results gracefully.
03 — Tool Activation Gate (Three-Way Check)

All three conditions must be true

✓
Classification signals web search needed
ClassificationResult.needsWebSearch === true
✓
Agent descriptor includes web_search in its allowed tools
agent.allowedTools.includes("web_search")
✓
User's plan has web search feature enabled
plan.featureFlags.webSearch === true
If any check fails → tool is never passed to the LLM. It cannot be called.

Resolver: resolveAllowedTools()

Called in src/router/tools.ts during routing. Returns the final list of tool IDs that get passed to the LLM as function declarations.

if ( classification.needsWebSearch && agent.allowedTools.includes("web_search") && plan.featureFlags.webSearch === true ) { tools.push("web_search"); }

The resulting allowedTools[] is embedded in the RoutingDecision and passed directly to toolSpecsFor() which generates the JSON Schema declarations sent to the LLM.

04 — Step-by-Step Data Flow
1
Classifier detects search intent src/router/classifier.ts
The query is analysed via heuristic patterns (keywords like "what is", "latest", "find") and optionally a lightweight GPT-4o-mini call if confidence is below 0.7. The result includes intent: "search", complexity, and needsWebSearch: true. The classification result is cached in Redis for 60 seconds (SHA256 of query).
2
Agent dispatcher selects agent src/router/agentDispatcher.ts
Intent "search" maps to the research agent by default. For complexity: "complex", it routes to deep_research agent instead. The agent's allowedTools array then gates which tools are available. Only agents that list "web_search" in their descriptor can trigger a search.
3
LLM receives tool declarations and starts streaming src/models/providers/*.ts
The web_search function schema is passed to the provider (Anthropic/OpenAI/Gemini) as a tool declaration. The LLM decides when to call it and emits a tool_call event with its chosen query string. The stream pauses at this point — the worker takes over.
// ProviderEvent emitted by the streaming loop { type: "tool_call", toolId: "web_search", arguments: { query: "latest AI chip benchmarks 2025" }, callId: "call_abc123" }
4
executeTool() dispatches to webSearch() src/tools/index.ts → src/tools/webSearch.tool.ts
The worker calls executeTool("web_search", { query }, ctx). The switch dispatcher routes it to webSearch(). Engine selection happens here: Tavily is tried first for research/complex paths; Brave for everything else. The function returns a WebSearchResult object.
Brave Response Shape
web.results[]: { url: string title: string description: string ← snippet }
Tavily Response Shape
results[]: { url: string title: string content: string ← 400 chars }
5
Subagent summarises top results src/runtime/subagent.ts
After raw results arrive, webSearch() spawns a summarise_pages subagent for each of the top 3 URLs (only when ctx.jobId is present). Each subagent is a lightweight GPT-4o-mini call (nano tier, 300-token output) that receives the title + snippet + URL and returns a 3-bullet factual summary. Subagent cost is attributed back to the parent job in api_calls.metadata.subagentCost.
🧩 summarise_pages Subagent
Input
"{title}\n{snippet}\n{url}"
Output
• 3-bullet factual summary • max 300 tokens • nano model tier
🗄️ Logged to: subagent_runs table
💰 Cost: added to parent api_calls.metadata
⚡ Parallel: up to 3 subagents at once
6
Search result re-injected into LLM context src/workers/chat.worker.ts
The complete WebSearchResult (results + summaries) is serialised to JSON and added to the message history as a role: "tool" message. The LLM stream resumes with this new context — it can now synthesise the search results, quote facts, and decide whether to call more tools or produce a final answer.
// Injected back as tool result message { role: "tool", toolCallId: "call_abc123", toolName: "web_search", content: JSON.stringify(webSearchResult) }
7
Citation accumulation & postProcess P4 — agent hook
While processing tool results, the worker accumulates a citations[] array from every web_search result. After the LLM stream finishes, the agent's postProcess hook appends a formatted source list if the LLM didn't already include one.
📎 Citation Assembly (postProcess hook)
if (!content.includes('## Sources')) { content += `\n\n---\n**Sources**\n` + citations.map(c => `[${c.index}] [${c.title}](${c.url})` ).join('\n'); }
05 — web_fetch: Full Page Retrieval

What is web_fetch?

web_search returns snippets — typically 400 characters of content. For deep research, that's not enough. web_fetch fetches the full URL, strips all navigation/ads/boilerplate using @mozilla/readability + jsdom, and returns clean article text up to a configurable character limit.

Input: { url: string }
Output: { title, text, url }

How readability extraction works

1
Fetch raw HTML via fetch(url) with 10s timeout
2
Parse into DOM via jsdom
3
@mozilla/readability strips nav, ads, sidebars — keeps article body
4
Truncate to MAX_FETCH_CHARS (default 12,000 chars) → return clean text

Strict Grounding Rule

The deep_research system prompt enforces that the LLM can only state facts that appear in retrieved sources. It cannot use training knowledge to fill gaps. If a source doesn't contain the answer, it must say so explicitly. Every factual claim must end with a citation [n].

10 — Key Concepts Summary

🟠 Brave as Default

Every web search defaults to Brave unless the calling agent is research/deep_research or complexity is complex. This keeps costs low for the majority of queries which don't need AI-native depth.

🟣 Tavily for Depth

Tavily is an AI-native search API — results include longer content excerpts and are optimised for LLM consumption. Reserved for tasks where answer quality matters more than cost: research agents and complex queries.

🔵 Subagent Summarisation

Rather than passing raw snippets to the main LLM, search results are compressed into 3-bullet summaries by a tiny nano-tier subagent. This compresses context consumption and improves relevance of what the main LLM sees.

🟢 web_fetch for Full Content

Snippets are 400 chars. Articles are 10,000+ words. The deep_research agent bridges this gap by fetching full page content, using readability to extract the article body, and truncating to a manageable size for the LLM.

🔷 Citation Grounding

Citations are tracked structurally (not just asked for in prompts). The worker accumulates a typed Citation[] array from tool results and the postProcess hook appends them as a verifiable source list — stored permanently in messages.citations JSONB.

🩷 Three-Way Gate

Web search is never accidentally available. Classifier must signal it. The agent must declare it. The plan must enable it. If any layer says no, the tool declaration is never sent to the LLM — it literally cannot be invoked.
